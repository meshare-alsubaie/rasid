# RASID (راصد)

**Watches 115 Saudi organisations for cooperative-training openings, and tells
you the moment one appears.**

→ **[meshare-alsubaie.github.io/rasid](https://meshare-alsubaie.github.io/rasid/)**

## The problem

Saudi universities require a cooperative training placement — التدريب التعاوني —
to graduate. Organisations announce their intakes with no advance calendar, on
their own websites, in Arabic, and the window stays open for seven to sixteen
days. There is no central listing. Missing the one announcement that matches
your degree costs a semester.

Checking a hundred career pages by hand, four times a day, for months, is not
something a final-year student can do. So this does it.

## What it does

Every six hours it reads 403 pages across 115 organisations, notices which ones
changed, asks Claude whether the change is a training announcement and whether
it matches this student's degree, and pushes a notification to his phone if it
does. It reads the deadline in either calendar, converts Hijri dates against the
Umm al-Qura table, and wakes him for a window closing inside forty-eight hours
even in the middle of the night.

It also watches each organisation's `sitemap.xml`, so an announcement published
at an address nobody has ever seen before is still found.

## The constraint that shaped everything

**The app is never allowed to imply certainty it does not have.**

That sounds like a slogan until you try to build it. A tracker that says
"nothing today" when it has silently stopped reading is worse than no tracker,
because the student stops checking. So:

- Every fact carries where it came from. Unknown is `null` and renders as
  "not announced" — never as a plausible default. The compiler enforces it:
  a display function takes `Attested<T>`, so a value with no recorded
  provenance cannot be rendered without saying so in code.
- A link is only watched after someone opened it and read it, and the note
  recording what was seen is quoted back in the interface. URLs are never
  generated by pattern — `example.com/careers` working is not evidence that
  `other.com/careers` exists.
- The home screen states how many sources were actually read out of how many
  are configured, how many organisations have no readable source at all, and
  when the last successful round finished — without being asked.
- When the crawler stops, when the classifier stops, or when no notification
  has arrived in a week, the app says so in red. Silence is never presented
  as good news.
- A page that stops mentioning training does not delete the opportunity it
  used to hold. It flags it and reports it.

The full list of what it cannot do is in [BACKLOG.md](BACKLOG.md), written in
the same voice.

## Architecture

```
Windows scheduled task (Riyadh)          GitHub Actions (cron, 6-hourly)
  sitemap diff -> fetch -> extract  ...    same pipeline, US address
  -> classify (Claude) -> commit -> push
                                    |
                          data/*.json committed to git
                                    |
                    decide what is newly true -> Web Push -> phone
                                    |
                    static PWA on GitHub Pages, offline capable
```

No server, no database, no accounts. The dataset is committed to the repository,
which gives it a full version history — "when did this organisation first
announce?" is answerable years later — and lets a data-only commit republish the
site without a rebuild.

Collection runs on a laptop in Riyadh as well as on GitHub, and that is not an
accident: a large share of `.gov.sa` hosts refuse a United States runner. Nine
of the eleven failures in the first cloud run were Saudi government sites that
answer a Saudi address without complaint.

**Stack:** Node 22 + TypeScript, `undici` for polite fetching, `@mozilla/readability`
for extraction, the Claude API for classification, Ajv for schema enforcement,
vanilla TypeScript + Vite for the PWA. No React, no component library.

## Repository layout

```
data/        the committed dataset: organisations, aggregators, opportunities,
             health, and verification (the link audit trail, failures included)
schemas/     JSON Schema mirrors of the types, enforced in CI
scripts/     validate.ts - schema + honesty checks
src/         types.ts - the canonical TypeScript types
```

## How a link earns its place

URLs are never generated by analogy. `example.com/careers` resolving is not
evidence that `other.com/careers` exists, and a page returning 200 is not a
careers page just because it loaded. Every stored link therefore carries:

- `provenance` - `official` only if the page was opened and read, `reported`
  for an unopened lead. `inferred` is not a legal value for a link.
- `verifiedAtISO` - when it was actually opened. `null` means never opened.
- `verifiedNote` - one line stating what was seen there.

`manualCheckUrl` is the link the user personally taps, so it is held higher
than the rest: the validator rejects an unopened lead in that field outright.
Unopened leads are still allowed in `sources`, where they are marked and
skipped by the pipeline rather than trusted.

Every check, including the ones that failed, is appended to
`data/verification.json`. Keeping the negative results is what lets the
validator report honestly how many links are verified, how many failed, and
how many targets have never been looked at.

## The collector

```bash
npm run collect                  # every verified source
npm run collect -- --limit 5     # small run
npm run collect -- --dry-run     # fetch and report, write nothing
```

It fetches only sources with a `verifiedAtISO`, at most two requests at a time,
never less than 1.5s apart to the same host, 20s timeout, two retries with
exponential backoff. `robots.txt` is consulted once per origin and cached; a
`4xx` on it means no rules exist, while a `5xx` or a network failure is treated
as disallow, because a briefly broken server has not granted permission.

Each page is reduced to its main text with Readability, falling back to stripped
body text when a page is rendered by JavaScript, and the SHA-256 of that text
goes in `data/snapshots.json`. A run only marks a source as changed when the
hash moves, which is what keeps the classifier bill near zero on quiet days.

Nothing fails the run. A page that times out, gets blocked by robots, or returns
no readable text is written into `data/health.json` with the reason, so the
interface can say which sources it can no longer see. Note that the spec's
thresholds call a single failure `healthy`, so the collector also prints how
many records carry a live error.

Set `RASID_CONTACT` to put a reachable address in the User-Agent:

```bash
RASID_CONTACT="you@example.com" npm run collect
```

## The classifier

The same run asks Claude whether the changed text is an announcement this
student can apply to, and writes the verdicts to `data/opportunities.json`.
Only text that is owed a verdict is sent: what changed this run, plus anything
a previous run failed to judge. On a quiet day that is nothing, and a quiet day
costs nothing.

```bash
npm run collect                    # classify what moved
npm run collect -- --reclassify    # classify everything fetched
npm run collect -- --no-classify   # network only, no model
npm run test:classifier            # failure branches, offline and free
npm run test:classifier -- --live  # two synthetic announcements, real spend
```

Model: `claude-sonnet-5` at **$2 / MTok input and $10 / MTok output**, checked
against platform.claude.com/docs/en/about-claude/pricing on 2026-08-29 rather
than from memory. That page also notes the launch pricing is now the standard
price and the increase to $3/$15 once scheduled for 2026-09-01 will not happen.
A full pass over the 17 sources readable at the time cost $0.18. Only the blocks
of a page that changed are sent (spec 5.3), so a quiet six hours costs nothing
and a page that moves costs a paragraph rather than six thousand characters.

**A failure never scores zero.** Zero means "not relevant to him". When the API
call fails, the reply will not parse, or it does not match the schema, the
record is stored with `relevanceScore: null` and a `needs_manual_review` flag,
the content hash is kept, and the source stays queued for the next run. The
four branches are asserted in `npm run test:classifier`, which needs no network.

`ANTHROPIC_API_KEY` is read from the environment and is never written to a file
or a log. `.env` and `.env.*` are gitignored.

## The app

An installable PWA, Arabic and right-to-left, built with Vite and plain
TypeScript. It reads the committed JSON at runtime, so a collection run
republishes the site without a rebuild.

```bash
npm run dev       # http://localhost:5173
npm run build     # dist/, with data/ copied in
npm run preview
```

The **Season Bar** is the signature element: September to February on one axis,
a thin lane per watched organisation, a hairline for today. A lane can only draw
a filled window when an announcement published dates. With none it shows `?`,
and a source that can no longer be read is greyed with a warning. Nothing in the
app can draw an inferred window, because nothing in the dataset infers one.

Every screen keeps the same rule as the pipeline. The three decision chips have
a third state that looks like neither yes nor no, a record the classifier could
not judge shows `؟` rather than a zero, and a load failure says it is a fault in
the app rather than an absence of openings.

## Running it for real

1. **Pages** — repository settings, Pages, source "GitHub Actions".
2. **The student profile.** This repository is public and is about
   organisations; the one thing in it that describes a person lives outside it.
   Copy `.profile.example` to `.profile.local`, which is gitignored, and put
   the same text in a `RASID_STUDENT_PROFILE` secret for CI. Without it the
   classifier refuses to run rather than judging against a blank profile.
   `npm run audit:privacy` runs in CI on every push, because git
   remembers what is deleted.
3. **Secrets** — `ANTHROPIC_API_KEY` for the classifier, and optionally
   `RASID_CONTACT` to put a reachable address in the crawler's User-Agent.
4. **Notifications**, all optional, each off until its secret exists:
   ```bash
   npx web-push generate-vapid-keys
   ```
   Store the pair as `VAPID_PUBLIC_KEY` and `VAPID_PRIVATE_KEY`. Open the app,
   Settings, "فعّل التنبيهات على هذا الجهاز", and paste what it prints into a
   secret named `RASID_PUSH_SUBSCRIPTION`. That subscription is the only place
   this design stores a device, which is how it keeps the spec's promise of no
   database. For the daily digest add `RESEND_API_KEY` and `NOTIFY_EMAIL`.
   Quiet hours default to 23:00–07:00 **Riyadh time** via `RASID_QUIET_START` /
   `RASID_QUIET_END` — measured in Riyadh whatever timezone the runner keeps —
   and no more than six pushes go out in a day. Nothing held back is discarded:
   what does not go out is queued in `data/pending-notices.json` and sent by the
   next run that is allowed to send.
5. **Schedule** — `.github/workflows/collect.yml` runs every six hours, collects,
   classifies, notifies, commits the dataset, and deploys. Installing Chromium
   for the rendered sources is allowed to fail without failing the run. See
   "Where the collection actually runs" below: the reading that matters happens
   on the owner's machine, and this workflow answers its push.

```bash
npm run check           # types, schemas, honesty rules
npm run test:classifier # four failure branches, offline and free
npm run test:notify     # what earns a notification, and what never does
npm run audit:contrast   # 4.5:1 measured on every screen, not asserted
npm run audit:privacy    # nothing personal in any tracked file
npm run audit:lighthouse # spec 8.7: performance >= 90, accessibility >= 95
```

## Local use

```bash
npm install
npm run check      # typecheck + validate
```

`npm run validate` fails the build on any honesty violation and prints coverage:
how many organisations still have no verified source, link, or application
channel. Warnings are deliberate. They are the app's to-do list.

## How it is held down

Seventeen gates run in CI on every push, and the interesting ones are not the
unit tests:

| Gate | What it holds |
|---|---|
| `test:gates` | **plants a fault in each of the other gates and fails if it is not caught** |
| `test:lifecycle` | a window opens by the calendar, not by the page changing; a record is never deleted for going quiet |
| `test:hijri` | thirteen real date phrasings, both spellings of the ambiguous months, and 209 round trips through the Umm al-Qura table |
| `test:faults` | twelve injected faults — dead DNS, soft 404, 40 MB page, redirect loop, robots refusal — each must produce a state the user can see |
| `test:longrun` | four failures that only appear months in, and the day he learns about each |
| `test:benchmark` | twenty real announcements against the spec's score bands: every graduate-development programme scores exactly 0, every cybersecurity one 90+ |
| `test:extract` | every page that has ever broken extraction, kept as a fixture |
| `test:scripts` | the collector's own entry point parses — two typographic dashes in a comment once stopped it, silently |
| `audit:contrast` | 4.5:1 measured on five themes × four screens, composited, including SVG |
| `audit:lighthouse` | performance and accessibility, measured rather than asserted |
| `audit:privacy` | no key, no grade, no personal detail — in tracked *or* staged files |

`test:gates` exists because a gate passed twice while checking nothing: a
`tsconfig` that excluded the entire browser half, and a privacy scanner that
read only committed files. Both were caught by audit rather than by testing,
which is the wrong way round. A checker that cannot be made to fail is not a
checker.

## Where the collection actually runs

Not only on GitHub, and this is worth knowing before reading the workflow.

GitHub's runners are in the United States and a large share of `.gov.sa` hosts
refuse them: nine of the eleven failures in the first cloud run were Saudi
government sites that answer the owner's own machine without complaint. So the
reading happens on that machine, on a six-hourly scheduled task
(`scripts/scheduled-run.ps1`), which commits the dataset and pushes. GitHub
answers that push by deciding what is newly true, sending the notifications, and
republishing the site — the half it does well. The cron in
`.github/workflows/collect.yml` still runs, and covers everything reachable from
the United States.

## Deliberate deviations from the specification

All of them come from spec section 4, "do not invent values for unverified
fields", and each is marked `DEVIATION FROM SPEC` in `src/types.ts`:

1. `Organisation.manualCheckUrl` and `applyVia` are nullable. Most entries still
   have no link anyone has opened and read.
2. `Sector` gained `finance`; `SourceType` gained `site_root`, so a homepage is
   never labelled a careers page.
3. `OpportunityStatus` gained `unknown`, for a programme with no published dates.
4. `SourceHealth.state` is `degraded` after a single failure, not after two.
5. `MAX_BROWSER_SOURCES` was raised from 8 to 30 once collection moved off a
   metered runner.
6. Predicted "متوقع" lanes in the Season Bar are not drawn. Prediction needs
   previous cycles, and this dataset has none of its own yet; a hatched bar
   would be an invention wearing a legend entry.

The validator counts every `null` in these fields and reports it, so the gap is
tracked rather than papered over with a plausible-looking link.

## Seed data provenance

The seed was written from the project specification only. Values appear in it
only where the specification stated them explicitly: Aramco's published
zero-courses condition, the Digital Government Authority's published conditions
that contain no such clause, Wadi Makkah's verified 2025 major list, and four
dedicated application emails. Everything else is `null` with
`provenance: "unknown"` and is waiting on the pipeline.

## What building this actually taught

Three of the worst defects in this repository were found by audit, not by
testing, and all three had the same shape: **a failure that looks like a
legitimate result.**

A window's status was computed once and stored, so a window that opened the
following week stayed filed under "announced, not open" for its whole life —
and nothing was broken, no error was raised, every source was green. A page that
stopped mentioning training deleted the opportunity it held, silently, and the
lane stayed green. A Hijri month whose name was matched only half-way failed as
"no year was written", which is a legitimate outcome the code produces on
purpose — so four months in twelve silently produced no date at all.

None of those raises an exception. None fails a schema. A test suite written by
the person who wrote the code tends to test the paths that person was thinking
about, and those three were exactly the paths nobody was thinking about.

What worked was adversarial review with a standing rule: *no claim without a
pasted command output.* Not "it handles this" — the command and what it printed.
That is why `test:gates` exists, and why the honesty rules are enforced by the
compiler and by a validator that fails the build rather than by anyone's care.

The other lesson is smaller and more practical: this is a tool for one person
with a deadline, not a product. Every choice about scope was made against one
question — *could this let a real window pass unseen?* Everything that could is
fixed. Everything that could not is written down in
[BACKLOG.md](BACKLOG.md) and deliberately left there.
